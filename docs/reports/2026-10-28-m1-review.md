## 1. `auditrail/verify.py` + `auditrail/cli.py`（verify-run，契约 C6）

### 通过项

- **纯只读**：`verify.py` 全文件只有 `read_text`；其调用的 `validate_judge_evidence` / `assess_dimensions` / `assess_run_quality` 经核实均无写路径（evidence.py / dimensions.py / tools.py 相应函数只读产物）。`_judge_proposal_view` 以 `copy.deepcopy(stored)` 起步，所有剥离/恢复都在内存副本上进行，绝不写回 run 目录。
- **退出码契约**：全 match = 0（`return 0 if result["ok"] else 2`）；任一 mismatch = 2；缺 `agent_judge.json` = 2（`FileNotFoundError` 被 CLI 捕获并输出干净错误，非崩溃栈）。测试 `test_cli_verify_run_match_exit_zero` / `mismatch_exit_two` / `missing_report_clean_error` 钉住三种情况。
- **重放口径与写路径一致**（重点核对）：
  - 写路径 Stage 1 只覆盖裁判原始提案；重放视图剥离 quality finding、确定性 check、规则证据与 score_trace 后重算，等价。
  - 写路径 `assess_dimensions` 在 quality 合并后的报告上执行，但 `overall_status` 在 `_merge_quality_report` 时已定型且之后不变，stored 值即写时输入值，重放等价；quality finding 是否在场只影响 `evidence_citation` 规则的证据内容，不影响被比对的 `final_score`。
  - 存储的 `judge_reliability` 是 downgrade（fact→inference、维度→unknown）**之前**算的，重放用 downgrade 之后的已存报告；经核实 `_collect_evidence` 不按 finding 类型或维度 status 过滤证据行，coverage / invalid_evidence_count 两项被比对字段不受 downgrade 影响，比对自洽。
- **judge 来源维度显式标注"不在校验范围"**，旧格式报告（无 score_trace / judge_reliability / metrics）逐项 skip 而非报错。
- **真实 run 抽样**（19 个已裁判 run）：17 个全 match；2 个 mismatch 为既有数据问题（见 §5），符合计划"记录为数据问题，不在 M1 修"的约定。

### 建议（不阻塞）

1. **边界路径缺测试**：`_judge_proposal_view` 中"judge_status 缺失但 judge_score 存在 → 按分数带恢复 status"与"judge_score 为 null → 恢复为 unknown/missing"两条路径无测试覆盖。现有测试只覆盖"完全没有 score_trace"的旧报告（整体 skip）。当前写路径里 `judge_score`/`judge_status` 成对写入（dimensions.py `_apply_rule` L132–134），这两条路径只在更老的报告上触发，属防御性代码，建议补两个针对性测试。
2. `_status_from_score` 与 `dimensions._status` 是两份独立的分数带实现，存在漂移风险；建议直接 import 复用。另外 `int(score)` 对非数值的 judge_score 会抛异常（见下条同类问题）。
3. `agent_judge.json` 内容损坏（非法 JSON）时 `json.loads` 异常未被 CLI 捕获，会以 traceback + 退出码 1 结束，与"明确报错而非崩溃"的契约精神不一致；建议与 `FileNotFoundError` 同样转成干净错误（退出码 2）。
4. `_judge_proposal_view` 按 `(category, title)` 剥离 quality finding、按已知 id 剥离确定性 check/规则证据：若裁判提案恰好与 quality finding 同名同类，或裁判自用了与确定性检查相同的 check id（如 `failure_detected`），会误删裁判自己的内容，可能制造误报 mismatch。发生概率低，建议在注释中标注该假设。

## 3. `evals/run_fault_injection.py`（契约 C2）

### 通过项

逐条对照 `evals/fault-injection/README.md` 断言语义，实现与文档一致：

- **档位语义 pass > partial > fail**：`_STATUS_RANK = {fail:0, unknown:0, partial:1, pass:2}`，实际 status 档位超过期望上限才判 `missed`；expect=partial 时 fail/partial → caught、pass → missed（`test_status_band_semantics` 钉住）。
- **unknown / 缺失 status 满足任何档位**：rank 0 不超过任何期望档，断言成立。
- **null completion_score → unverifiable**：不算 caught 也不算 missed（`test_completion_score_ceiling_and_null_unverifiable` 钉住）。
- **fault 判定**：任一断言违反 → missed；至少一条成立且无违反 → caught；全部不可评估 → unverifiable。与 README 逐字一致。
- 两类断言全无 → `ValueError` → 样本计 `skipped`（README："两者都没有的样本视为不可用"）✓；缺 run/缺报告 skipped 不中断 ✓；空目录 `0/0` 退出码 0 ✓；非 reviewed 样本跳过并单列提示 ✓。

### 观察（非问题）

- `totals` 中没有 `non_reviewed` 计数（只有 `non_reviewed_samples` 清单），因此 `totals.samples ≠ reviewed + skipped`；compare_judge 的 totals 有 provisional 计数，两工具口径略不齐，不影响正确性。
- 召回率分母含 unverifiable fault（`caught / faults`），与 README "caught/total" 字面一致且已被测试钉住；解读召回率时注意 unverifiable 会拉低该值。
